1. 한 줄 요약

점수 계산과 차단 기준(100점)은 그대로 두고, 화면에 보여 주는 값을 바꿉니다.
위험도(%) = min(점수 ÷ 차단 기준 100점, 1) × 100
단계는 정상 주의 위험 고위험 차단 다섯 개. 100점을 넘은 점수(150 등)는 차단 근거로만 남깁니다.

2. 왜 바꾸나

이전 문제원인
대시보드에 150점, 180점이 보여서 "100점이 최대인지" 알 수 없음 100점은 최대가 아니라 차단 기준선. 마지막 요청 점수와 보너스가 한 번에 더해져 기준을 넘은 값이 남음
150점과 120점 중 누가 더 위험한지 헷갈림 둘 다 "확정·차단"으로 같은 뜻. 차이는 마지막 요청과 보너스가 얼마나 붙었는지일 뿐
건수 기반 위험도(10건 10%, 50건 80% 등)는 현실에 안 맞음 BOLA 3건 정도면 이미 차단되므로 10건, 50건 구간이 쓰일 일이 없음

100점을 넘는 이유

judge/scoring.py는 이벤트를 더한 뒤 합계가 100 이상인지 봅니다. 그래서 넘어선 만큼이 남습니다.

/members/3 조회  BOLA_PATH +40                        =  40
/members/4 조회  BOLA_PATH +40                        =  80
/members/5 조회  BOLA_PATH +40 → 120 + 피해자 3명 +30  = 150  ★ 확정
  • 확정된 사용자는 그 뒤 이벤트를 채점하지 않으므로, 점수는 확정 순간의 값(150)에서 멈춥니다.
  • 이론상 최대는 99점에서 쓰기 BOLA(60)와 보너스 세 개(30+20+10)가 한 번에 붙은 219점입니다.

3. 점수가 매겨지는 과정

점수는 두 단계를 거쳐 매겨집니다. 탐지 엔진이 요청 하나를 4가지 종류로 판정하고, 판단 서버가 그것을 점수 항목으로 나눠 점수를 더합니다.

요청 1건 (Kong 로그)
   │
   ▼  ① 탐지 엔진 (fluent-bit/realtime.py) ─ 장부(ledger.json)와 비교
   │     403/404                     → ATTEMPT
   │     장부에 없는 객체             → UNKNOWN
   │     200/204 + 요청자 ≠ 장부 주인 → BOLA
   │     10초에 의심 요청 10번 초과    → RATE (+ 10분 임시 차단)
   │     본인 객체, 정상               → 보고 안 함
   │
   ▼  ② 판단 서버 (judge/scoring.py) ─ 점수 항목으로 분류
   │     BOLA    + URL 번호가 곧 주인인 API (/members/{id} 등) → BOLA_PATH   (쓰기면 BOLA_PATH_WRITE)
   │     BOLA    + 그 밖의 API (장부 근거)                    → BOLA_LEDGER (쓰기면 BOLA_LEDGER_WRITE)
   │     UNKNOWN + URL 번호가 곧 주인인 API + 성공             → BOLA_PATH 로 올림
   │     ATTEMPT / UNKNOWN / RATE                             → 그대로
   │
   ▼  ③ 사용자별로 항목 점수 + 보너스를 누적 → 위험도 % → 단계
  • 쓰기 = PUT, PATCH, DELETE (남의 객체를 수정·삭제). 조회보다 20점 높습니다.
  • URL 번호가 곧 주인인 API(path_owners)는 판단 서버가 학습 장부로 자동 추론합니다. 지금은 /members/{id}, /profiles/{id} 두 개입니다.
  • 점수 값은 모두 judge/config.json의 points, bonus에서 바꿀 수 있습니다.

7-1. 단계 경계를 정한 이유

경계는 그 점수에 닿으려면 실제로 무엇을 해야 하는지를 보고 정했습니다.

단계경계닿는 행동이유
주의10403/404 2번남의 번호를 찔러보는 탐색. 1번(5점)은 오타일 수 있어 정상
위험30남의 것을 1번 봄 (BOLA 1건)BOLA 1건이 처음 닿는 점수
고위험60남의 것을 2번 봄, 또는 쓰기 1번자동 차단 전에 사람이 확인할 지점 → 관리자 알림
차단100남의 것을 3번 봄, 또는 쓰기 2번1~2번은 실수일 수 있지만 3번은 우연이 아님 → 영구 차단
  • 30·60·100은 원래 쓰던 경계라서 차단과 알림 시점은 그대로입니다. 회의 안대로 주의(10)만 새로 생겼습니다.
  • 차단 기준이 100이라 점수 = 위험도(%) 입니다.
한계: 팀에서 정한 값이고 실제 데이터로 검증하지는 않았습니다 (개선 사항 4번).

7-2. 실무와 비교

위험도는 실무와 같이 0~100 척도로 표시하며, 근거는 탐지 항목별 점수의 누적입니다.

실무에서도 위험도를 0~100 척도로 나타내고 구간마다 등급과 조치를 연결하는 경우가 많습니다. 표시 방식은 비슷하지만, 숫자를 만드는 근거는 제품마다 다릅니다.

근거쓰는 곳 (예)우리
규칙 점수 합계보안 관제(SIEM)의 위험 기반 경보, 웹 방화벽 이상 점수이 방식
머신러닝 확률결제 사기 탐지, 봇 탐지—
평소 행동 대비 이상 정도사용자 행동 분석(UEBA)—
  • "45%"는 "공격일 확률 45%"가 아니라 "100점 척도에서 45점"이라는 뜻입니다.
  • 실무의 일반적인 등급 구간(예: CVSS를 100점으로 바꾼 40 / 70 / 90)보다 우리 경계(10 / 30 / 60)가 낮은 이유는, BOLA는 한 건만으로도 실제 데이터 유출이라 단계를 일찍 올리도록 했기 때문입니다.
  • 위 실무 사례는 일반적인 지식을 정리한 것이라, 보고서에 인용할 때는 각 제품의 공식 문서로 확인이 필요합니다.
