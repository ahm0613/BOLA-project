2. 준비 단계: 장부 학습

탐지는 "이 객체의 주인이 누구인가"를 알아야 할 수 있습니다. 그래서 설치 전에 과거 로그로 장부(ledger)를 만듭니다.

fluent-bit/ledger_v2.py수동 과거 로그 → 객체별 주인 장부
입력data/access_fake.json (Kong 형식 로그), confirmed.json(제외할 요청·사용자)
출력ledger_days/날짜.json(날짜별 집계), ledger.json = {API: {객체ID: 주인 또는 null}}

동작 순서

  1. 학습 대상 고르기 (is_learnable): 상태 200, role=user, 로그인 사용자, Kong이 막지 않은 요청만 씁니다.
  2. 제외 (is_excluded): confirmed.json의 확정 요청, 그리고 확정 사용자의 확정 시각 이후 요청을 뺍니다. 공격 흔적으로 장부가 오염되지 않게 하려는 것입니다.
  3. 날짜별 집계 (build_days): 어제부터 30일치(WINDOW_DAYS)를 한 줄씩 읽어 "그날 누가 어떤 객체를 몇 번 봤나"를 셉니다. 목록 응답의 resp_ids에 나온 객체도 그 사용자가 본 것으로 칩니다. 이미 만든 날짜는 재사용하고, confirmed.json이 바뀌면 다시 만듭니다.
  4. 상한(cap) (compute_cap): 한 사람이 하루에 같은 객체를 수십 번 새로고침해도 표가 몰리지 않게, 하루 몇 번까지만 셀지 정합니다. 사용자별 99퍼센타일의 중앙값을 쓰고 2~10 범위로 제한하며, 한 번에 1씩만 바뀝니다.
  5. 주인 결정 (merge → decide_owner): 30일 합산에서 한 사용자의 몫이 70% 이상(MIN_SHARE)이면 그 사용자가 주인이고, 아니면 null(공유 객체, 판정하지 않음)입니다.
fluent-bit/ledger_v3.py수동 · 설치할 때 한 번 설치 전 로그의 BOLA 사용자 → confirmed.json
입력ledger_days/, ledger.json(1차 장부), 원본 로그, judge/config.json(path_owners, path_infer), judge/api_infer.py
출력confirmed.json의 users(사용자 → 처음 공격한 날 00:00)와 requests(공격 요청 ID). 1대1 API 목록은 화면에만 출력하고 저장하지 않음

동작 순서

  1. 1대1 API 정하기 (resolve_path_owners): judge와 같은 규칙으로 "URL 번호 = 사용자 번호"인 API를 정합니다. judge가 켜져 있지 않아도 됩니다. ①단계(ledger_v2.py)에서 이미 만든 ledger.json만 있으면 추론할 수 있습니다.
    config.json의 path_owners사용하는 목록
    "auto" (지금 설정)judge/api_infer.py의 infer(ledger) 결과. judge와 같은 함수, 같은 path_infer 기준(표본 30↑, 일치율 95%↑)
    목록 (예: ["/members/{id}"])그 목록 그대로. []이면 URL 판단을 끔
    설정 없음코드의 기본값 DEFAULT_PATH_OWNERS (/members/{id}, /profiles/{id})
    [1대1 추론] /members/{id}   표본 2055건, 일치 2055건 (100.0%) → 1대1
[1대1 추론] /profiles/{id}  표본 1978건, 일치 1978건 (100.0%) → 1대1
[1대1 추론] /orders/{id}    표본 2977건, 일치    2건 (  0.1%) → 장부 사용
[1대1 추론] path_owners = ['/members/{id}', '/profiles/{id}']

    2026-11-06 수정 전에는 "auto" 문자열을 경로 목록으로 잘못 읽어서([['a'],['u'],['t'],['o']]) URL 판단이 꺼져 있었습니다. 그래서 장부에서 빠진 회원·프로필 객체를 피해자로 세지 못했습니다.

  2. 의심 사용자 찾기 (find_suspects): 사용자별 30일치 기록에서 "남의 것"을 셉니다.
    • ⓪에서 정한 1대1 API는 장부를 보지 않고 URL 번호로 주인을 판단합니다 (path_foreign). 장부에 빠진 객체도 셀 수 있습니다.
    • 그 밖의 API는 ledger.json의 주인이 요청자가 아니면 남의 것입니다 (foreign). 주인이 null인 객체는 셀 수 없습니다.
    • 서로 다른 피해자가 3명 이상(--min-victims)이면 의심 사용자로 봅니다.
  3. 공격 요청 모으기 (collect_requests): 원본 로그에서 그 사용자의 BOLA(200, 남의 것)와 ATTEMPT(403/404) 요청 ID를 모읍니다. 주인 판단에는 ⓪의 1대1 목록을 똑같이 씁니다.
  4. 합치기 (merge_confirmed): 기존 명단은 지우지 않고 추가만 합니다. 관리자가 해제한(released) 사용자는 다시 넣지 않습니다.
  5. 안전장치 (judge_status): judge 소비자가 최근 15초 안에 Redis를 읽었으면 실행을 거부합니다. 켜진 judge가 파일을 덮어쓰기 때문입니다.
설치 순서
  ① python ledger_v2.py            1차 장부
  ② python ledger_v3.py --dry-run  미리 보기 → python ledger_v3.py   confirmed.json에 합침
  ③ python ledger_v2.py            confirmed.json의 사용자·요청을 빼고 다시 학습 → 깨끗한 ledger.json
  ④ docker compose up -d           judge가 켜지면서 confirmed.json 명단을 영구 차단

3. 탐지: realtime.py

fluent-bit/realtime.pyDocker bola-realtime · 포트 5170 로그 한 줄마다 즉시 판정
입력pc2 Fluent Bit이 TCP(mTLS)로 보내는 Kong 로그 한 줄 = 요청 하나. ledger.json
출력Redis bola:events에 이벤트(XADD, 최대 10만 건 유지), 임시 차단 키 blocked:user:N

연결

TLSServer가 certs/server.crt로 TLS를 열고, CA가 서명한 클라이언트 인증서가 없으면 연결을 거부합니다(CERT_REQUIRED). 연결마다 Handler 스레드가 한 줄씩 읽어 process()를 호출합니다.

process(e): 요청 하나 처리

  1. is_user_request: role=user이고 로그인했으며 Kong이 막지 않은 요청만 처리합니다. 관리자, 비로그인, 이미 차단된 요청은 무시합니다.
  2. reload_ledger: 60초마다 ledger.json이 바뀌었는지 확인하고, 바뀌었으면 다시 읽습니다. 실시간으로 추가한 객체는 유지합니다.
  3. add_from_list / add_from_created: 개인 목록(GET /orders)에 나온 객체와 방금 만든 객체(POST 201)를 요청자 것으로 장부에 추가합니다. 그래서 막 주문한 사람의 주문 상세 조회가 UNKNOWN으로 잡히지 않습니다.
  4. judge(e, ledger): 판정합니다 (아래 표).
  5. 의심 요청이면 report로 Redis에 보내고, count_suspicious로 최근 10초 안의 의심 요청 수를 셉니다. 10번을 넘으면 temp_block을 실행합니다.

judge(): 판정 규칙 (위에서부터, 처음 맞는 것)

#조건결과
1URL에 숫자 ID가 없음, 또는 장부에 그 API가 없음판정 안 함
2상태 403 / 404ATTEMPT
3장부에 그 객체 ID가 없음UNKNOWN
4장부의 주인이 null (공유 객체)판정 안 함
5상태 200/204이고 요청자 ≠ 주인BOLA "요청자 7 -> 3 (주인 3)"
6그 밖 (본인 객체)정상, 출력 안 함

same_object_apis: PATCH /members/{id}로 학습된 기록이 없으면 GET /members/{id}의 장부를 씁니다. 같은 객체는 메서드가 달라도 주인이 같기 때문입니다.

임시 차단 temp_block()

SET blocked:user:N "rate" EX 600 NX를 실행합니다. NX 옵션이라서 이미 키가 있으면(영구 차단 포함) 덮어쓰지 않습니다. 새로 걸었을 때만 RATE 이벤트를 보고합니다.

Redis 이벤트 모양

XADD bola:events MAXLEN ~100000 *
  kind=BOLA  user_id=7  api="GET /members/{id}"  uri=/members/3  status=200
  request_id=a1…  started_at=1793…  detail="요청자 7 -> 3 (주인 3)"

4. 판단: judge.py와 보조 모듈

judge/judge.pyDocker bola-judge 총괄: 받고, 채점을 맡기고, 결과를 내보냄
입력Redis bola:events (소비자 그룹 judges), config.json, .env
출력confirmed.json, Redis 영구 차단 키, PostgreSQL, Slack, output/*.jsonl

시작 순서 main()

  1. load_env, load_config: .env와 config.json을 읽습니다.
  2. Server.__init__: Redis 클라이언트(연결 대기 5초), ConfirmedStore, Judge, DbWriter, Blocker, Notifier를 만듭니다. path_owners: "auto"이면 api_infer로 1대1 API를 먼저 추론합니다.
  3. 점수 복원 ① rebuild_db(): PostgreSQL bola_events를 스트림 ID 순서로 읽어 다시 채점합니다. 이미 DB에 있는 행이므로 다시 쓰지 않고(replaying=True), 사용자 상태가 바뀐 시각도 이어받습니다.
  4. 점수 복원 ② rebuild(): Redis에서 ①의 마지막 ID 이후, 즉 DB에 아직 못 쓴 이벤트만 보충합니다. Redis가 꺼져 있으면 3초마다 다시 시도합니다. DB를 못 읽었다면 Redis만으로 복원합니다.
  5. sync_blocks(force=True): confirmed.json에 있는데 Redis 영구 키가 없는 사용자를 다시 차단합니다.
  6. notifier.start(): 복원이 끝난 뒤부터 알림을 보냅니다. 과거 이벤트로는 알림을 보내지 않습니다.
  7. consume(): XREADGROUP으로 ① 받았지만 ACK 못 한 이벤트, ② 새 이벤트(5초 대기) 순서로 처리하고 ACK합니다. 그 사이 60초마다 상태 출력, 차단 키 동기화, 장부 변경 확인을 합니다.

judge/scoring.py모듈 분류 → 채점 → 단계 → 확정 (Redis·파일을 모르는 순수 로직)

classify(e): 이벤트 → 점수 항목

조건항목점수
URL 번호가 요청자 본인 (BOLA·ATTEMPT·UNKNOWN)없음 (장부 오탐으로 봄)0
path_owners API에서 BOLA, 또는 UNKNOWN인데 200/204 성공BOLA_PATH / BOLA_PATH_WRITE40 / 60
그 밖의 BOLA (장부 근거)BOLA_LEDGER / BOLA_LEDGER_WRITE30 / 50
장부에 없는 객체UNKNOWN20
임시 차단 발생RATE10
403 / 404ATTEMPT5

_WRITE는 메서드가 PUT/PATCH/DELETE일 때입니다. 남의 객체를 수정하거나 삭제하는 것이라 조회보다 점수가 높습니다.

score(): 합계와 보너스

  • +victims 30: 서로 다른 피해자 3명 이상
  • +attempt_then_bola 20: ATTEMPT 뒤에 BOLA 성공 (우회 경로를 찾았다는 뜻)
  • +multi_api 10: 자원 종류(members, orders 등) 2개 이상에서 BOLA

process(): 단계와 확정

  • 사용자별 이벤트 큐(recent)에 넣고 합계를 냅니다. window_sec: 0이면 오래된 이벤트를 빼지 않고 영구 누적합니다.
  • 단계: normal → watch(30) → warning(60) → attack(100, 확정). 단계는 올라가기만 합니다.
  • URL로 확인된 BOLA(BOLA_PATH)는 사용자 확정과 상관없이 그 요청을 바로 확정합니다.
  • 100점 이상이면 사용자를 확정합니다. 확정된 뒤의 이벤트는 점수를 계산하지 않고 요청 ID만 추가합니다.
  • 관리자가 해제한 시각(released) 이전의 이벤트는 채점하지 않습니다.
judge/api_infer.py모듈 "URL 번호 = 사용자 번호"인 API를 장부로 추론

정상 사용자는 자기 것만 봅니다. 그래서 /members/{id}는 학습된 주인이 URL 번호와 항상 같고(225 = 225), /orders/{id}는 거의 다릅니다(1203 ≠ 400).

표본 30개 이상이고판정쓰임
일치율 95% 이상1대1path_owners에 넣음 → BOLA_PATH로 채점
일치율 5% 이하장부 사용BOLA_LEDGER로 채점
그 사이 / 표본 부족판단 보류쓰지 않음

Redis, DB, judge 상태를 모르고 장부 dict만 받는 함수(infer(ledger) → (path_owners, 통계))라서 두 곳에서 같이 씁니다.

  • judge.py: 시작할 때 추론하고, 60초마다 ledger.json의 수정 시각을 확인해서 바뀌었으면 다시 추론합니다.
  • ledger_v3.py: 설치할 때 1차 장부로 추론합니다 (judge가 꺼져 있어도 됨). 그래서 설치 전 판정과 실시간 판정이 같은 1대1 기준을 씁니다.

결과는 파일로 저장하지 않고 각 프로세스의 메모리에서만 씁니다. 단독 확인: cd judge → python api_infer.py ..\fluent-bit\ledger.json

judge/store.py모듈 confirmed.json = 영구 차단 명단 + 학습 제외 목록
{"requests": ["979917aa-…", …],        확정된 공격 요청 → ledger_v2.py 학습에서 제외
 "users":    {"7": 1793…},             확정 사용자 → 확정 시각(ms). 영구 차단 명단
 "released": {"9": 1793…}}             관리자가 해제 → 이 시각 이전 이벤트로는 다시 확정 안 함

apply()는 확정을 반영하고 근거(점수 내역, 피해자, 요청 수)를 output/confirmed_log.jsonl에 한 줄씩 남깁니다. save()는 임시 파일에 쓴 뒤 바꿔치기해서 쓰다 만 파일이 읽히지 않게 합니다. 한 번 들어간 사용자는 judge가 지우지 않습니다(해제는 unblock.py로만).

judge/blocker.py모듈 Redis 영구 차단 키
blocked:user:7   "confirmed"   TTL 없음 (영구)     ← pc2 Kong이 요청마다 확인, 있으면 403
block:info:7     {reason, blocked_at, by}           ← 사람이 확인하는 용도
  • block_forever: 확정되는 순간 차단합니다. Redis 오류가 나도 예외를 던지지 않고 False를 돌려줘서 판단이 멈추지 않습니다.
  • not_blocked / sync: 60초마다 confirmed.json 명단과 비교합니다. 키가 없거나(TTL -2), RATE 10분 키로 덮여 만료가 붙은 사용자는 다시 영구로 겁니다.
judge/db.py모듈 PostgreSQL 기록과 점수 복원 조회

쓰기: DbWriter

  • 판정 루프는 put_event와 put_user로 메모리 큐에 넣고 바로 돌아갑니다. DB가 느려도 판단이 느려지지 않습니다.
  • 저장 스레드가 1초(flush_sec)마다 큐를 비워 한 트랜잭션으로 씁니다. bola_events는 ON CONFLICT DO NOTHING이라 중복되지 않고, user_status는 사용자마다 마지막 값만 씁니다.
  • DB가 꺼져 있으면 큐에 쌓아 두고(최대 1만 건) 다시 연결되면 씁니다.
  • 10초(sweep_sec)마다 만료된 RATE 임시 차단을 expired로 바꿉니다.

읽기: read_events / row_to_event (점수 복원)

bola_events에서 스트림 ID 형식(숫자-숫자)의 행만, ID를 숫자로 나눠 정렬해서 서버 측 커서로 2,000건씩 읽습니다. 각 행을 Redis 이벤트 모양(kind, uri, detail 등)으로 되돌려 handle()에 넣습니다.

테이블한 행pc3에서
bola_eventsRedis 이벤트 1건 + 그 시점의 점수·판단 + 조치(AC-…-R 임시, AC-…-L 영구)탐지·조치 이력
user_status사용자 1명의 현재 상태와 점수지금 위험한 사용자
alerts보낸 Slack 알림 (중복 방지 키)알림 이력

상황동작하는 파일결과
