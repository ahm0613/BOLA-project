# BOLA 탐지 룰 설명서

bola-rule 엔진이 쓰는 Python 룰(BOLA-R1 ~ R6)을 설명합니다.
설정 값은 모두 `config.yaml`에 있고, 코드는 `bola_engine/rules.py`에 있습니다. 내부 동작 순서는 [RULE_FLOW.md](RULE_FLOW.md)를 참고하세요.

---

## 1. 무엇을 탐지하나

**BOLA(Broken Object Level Authorization)**: 로그인한 사용자가 URL의 ID만 바꿔 **남의 데이터에 접근해 성공**하는 공격입니다.

```
alice(1번)  GET /orders/2   → 200   ← 주문 2는 bob(2번) 것인데 성공
```

이 엔진은 Kong API 게이트웨이 로그만 보고, **"성공한(2xx) 요청 중 남의 객체에 접근한 것"**을 찾습니다.

### Wazuh 룰과의 역할 분담

| 담당 | 탐지 대상 | 예 |
|---|---|---|
| **Wazuh 룰** | 로그 한 줄이나 횟수로 판단할 수 있는 것 | 401 반복, 1분에 403/404가 N번 (ID 찔러보기) |
| **Python 룰 (이 엔진)** | **기억이 필요한 것** | "주문 2의 주인은 bob"이라는 사실을 알아야 판단 가능 |

`GET /orders/2 → 200`은 겉보기에 정상 요청과 똑같습니다. 주인이 누구인지 알아야만 공격인지 판단할 수 있어서 Python 룰이 맡습니다.

## 2. 판정 흐름

```
Kong 로그 1건
   │
   ├─ 판정 대상인가?  (로그인한 일반 사용자 · 2xx 성공 · Kong 차단 아님 · admin 아님)
   │      └─ 아니면 → 판정 안 함
   │
   ├─ 응답에 주인 정보가 있나?  ─ 있음 → [R1] 응답 주인 ≠ 요청자 ?
   │
   └─ 없음 → 경로 ID가 사용자 번호인 API인가?  ─ 예 → [R5] 경로 사용자 ≠ 요청자 ?
                 │
                 └─ 아니오 → 장부에 주인이 있나?  ─ 있음 → [R2] 장부 주인 ≠ 요청자 ?
                               │
                               └─ 없음 → 변경 요청이고, 요청자가 처음 건드리는 객체인가? → [R3]
   │
   ├─ 위반이 났으면 → 요청자별로 모아 → [R4] 짧은 시간에 피해자가 여러 명인가?
   │
   ├─ 장부 갱신 (응답·목록으로 확인된 주인, 위반 없는 방문 기록)
   │
   └─ (2xx·403·404 모두) 본인 객체가 아니면 → [R6] 짧은 시간에 연속된 ID를 훑었나?
```

| 룰 | 판정 단위 | 심각도 | 한 줄 요약 |
|---|---|---|---|
| **BOLA-R1** | 요청 1건 | high | 응답에 적힌 주인이 요청자와 다름 |
| **BOLA-R2** | 요청 1건 | high | 장부에 적힌 주인이 요청자와 다름 |
| **BOLA-R3** | 요청 1건 | medium | 주인을 모르는 객체를 처음 보는 사람이 변경함 (의심) |
| **BOLA-R4** | 사용자 | critical | 짧은 시간에 여러 피해자의 객체에 접근함 (사건 경보) |
| **BOLA-R5** | 요청 1건 | high | URL의 사용자 번호가 요청자와 다름 (`/members/2`를 1번이 요청) |
| **BOLA-R6** | 사용자 | medium | 짧은 시간에 남의 객체 ID를 연속으로 훑음 (정찰 경보, 403/404 포함) |

## 3. 장부(ledger)란

R2와 R3가 쓰는 **"객체 → 주인" 표**입니다. 로그를 읽으면서 계속 채웁니다. 파일은 `state/ledger.json`입니다.

| 기록 방법 | 근거 | 예 | 신뢰도 |
|---|---|---|---|
| **응답으로 확인** (`confirmed`) | 응답에 주인 필드가 하나로 나옴 | `GET /orders/2` 응답에 `user_id: 2` → "주문 2 = 2번" | 높음 |
| **목록으로 확인** (`confirmed`) | "내 목록" API에 나온 객체는 요청자 것 | bob이 `GET /orders` → `[7, 8]` → "주문 7, 8 = bob" | 높음 |
| **방문 기록으로 추정** (`inferred`) | 확인된 주인이 없을 때만 사용. 여러 날 중 70% 이상 한 사람이 조회 | | 보통 |

- 공격 요청의 응답이라도 **응답 속 주인은 사실**이므로 장부에 기록합니다.
- 위반이 난 요청은 방문 기록에 넣지 않습니다. 공격자가 주인으로 추정되는 것을 막기 위해서입니다.
- 여러 사람이 비슷하게 조회한 객체는 공유 객체로 보고 주인을 정하지 않습니다.

## 4. 룰 상세

### BOLA-R1: 응답 주인 불일치

| 항목 | 내용 |
|---|---|
| 조건 | 2xx 응답의 **주인 필드** 값 중 요청자가 아닌 사용자가 있음 |
| 주인 정보 출처 | Kong이 응답에서 뽑아 둔 `resp_ids` |
| 대상 API | `config.yaml`의 `owner_fields`에 적힌 API |
| 심각도 | high |

```
요청자 52  GET /orders/39 → 200
resp_ids: {"id": ["39"], "user_id": ["20"]}     ← owner_fields: "GET /orders/{id}": "user_id"
→ 52 ≠ 20 → BOLA-R1
```

현재 설정된 API는 다음과 같습니다.

| API | 주인 필드 |
|---|---|
| `GET /members/{id}`, `PATCH /members/{id}` | `user_id` |
| `GET /members/{id}/addresses` | `[].user_id` |
| `GET /members/{id}/addresses/{id}` | `user_id` |
| `GET /orders/{id}` | `user_id` |
| `GET /payments/{id}` | `user_id` |
| `GET /profiles/{id}` | `user_id` |

- **장점:** 요청 한 건만으로 판정되고, 서버가 알려 준 사실이라 가장 확실합니다.
- **한계:** 응답에 주인 필드가 없으면 판정할 수 없습니다. 빈 목록이거나, 64KB를 넘거나, gzip으로 압축된 응답은 Kong이 추출을 건너뜁니다. 이런 경우 R2로 넘어갑니다.
- **새 API 추가:** `owner_fields`에 한 줄을 추가하면 됩니다.

---

### BOLA-R2: 장부 주인 불일치

| 항목 | 내용 |
|---|---|
| 조건 | 응답에 주인 정보가 없을 때, **장부의 주인**이 요청자와 다름 |
| 주인 정보 출처 | 장부 (`confirmed` 또는 `inferred`) |
| 대상 API | URL에 객체 ID가 있는 모든 API 중 R1으로 판정할 수 없는 것 |
| 심각도 | high |

```
9/29 ~ 10/24  사용자 36  GET /orders → [91, 90]       → 장부: "주문 91 = 36번"
10/26 00:37   사용자 58  POST /orders/91/cancel → 200
              resp_ids: {"id": ["91"]}                   ← 응답에 주인 없음 → R1 불가
→ 장부상 주인 36 ≠ 요청자 58 → BOLA-R2
```

**객체를 정하는 방법:** URL에서 **마지막 숫자 ID까지**를 하나의 객체로 봅니다. 그래서 조회와 변경이 같은 객체로 묶입니다.

| URL | 객체(resource) | 객체 ID |
|---|---|---|
| `/orders/2` | `/orders/{id}` | `2` |
| `/orders/2/cancel` | `/orders/{id}` | `2` |
| `/members/1/addresses` | `/members/{id}` | `1` |
| `/members/1/addresses/5` | `/members/{id}/addresses/{id}` | `1/5` |

- **장점:** 응답 모양과 관계없이 판정할 수 있습니다. 취소나 수정처럼 피해가 큰 변경 요청도 잡습니다.
- **한계:** 장부에 아직 없는 객체(처음 보는 객체)는 판정하지 못합니다. 이 경우는 `unknown_owner`로 개수만 세고 R3로 넘깁니다.

---

### BOLA-R3: 목록 밖 객체 변경

| 항목 | 내용 |
|---|---|
| 조건 | ① 장부에 주인이 없고 ② **변경 요청**(POST/PUT/PATCH/DELETE)이며 ③ 요청자가 그 객체를 이전에 정상적으로 다룬 기록이 없음 |
| 성격 | 주인을 확정할 수 없으니 **확정 위반이 아니라 의심** |
| 심각도 | medium |

```
사용자 58  PATCH /orders/101/delivery-memo → 200
  · 응답에 주인 없음 (R1 불가)
  · 장부에도 주문 101 없음 (R2 불가)
  · 58번은 주문 101을 목록에서 본 적도, 다룬 적도 없음
→ BOLA-R3 (의심)
```

- **조회에는 적용하지 않는 이유:** 처음 보는 객체를 조회하는 일은 정상 사용에서도 흔하고, 조회는 피해가 상대적으로 작기 때문입니다.
- **장점:** R2가 놓치는 "주인이 나타나기 전의 공격"을 보완합니다.
- **한계와 주의:** 실제 서비스에서 "방금 만든 객체를 목록도 보지 않고 바로 변경"하는 정상 사용자는 걸릴 수 있습니다(이 앱에는 생성 API가 없어 시험하지 못함). 그래서 심각도를 medium으로 두었습니다.

---

### BOLA-R4: 다수 소유자 접근

| 항목 | 내용 |
|---|---|
| 조건 | 한 사용자의 R1~R3 위반을 모았을 때, 창(window) 안에 **서로 다른 피해 대상**이 기준 이상 |
| 판정 단위 | 요청이 아니라 **사용자**(공격자) |
| 성격 | 개별 위반을 묶은 **사건 경보**. 차단이나 분석 엔진 연동에 쓰기 좋은 신호 |
| 심각도 | critical |

**피해 대상을 세는 방법:** 주인을 알면(R1·R2) 그 주인을 셉니다. 주인을 모르면(R3) 객체 자체를 하나의 대상으로 셉니다.

**창(window) 두 개**는 `config.yaml`의 `rules.BOLA-R4.windows`에서 설정합니다.

| 창 | 기준 | 잡는 공격 |
|---|---|---|
| **급속** | 10분 안에 5명 | 몰아서 수집 (예: 9초 만에 회원 5명 조회) |
| **저속** | 24시간 안에 5명 | 의심을 피하려고 천천히 수집 (예: 1시간에 1~3명) |

```
[급속] 요청자 1이(가) 최근 10분 동안 피해 대상 5명/개의 객체에 접근해 위반 9건을 냄 (기준 5)
[저속] 요청자 58이(가) 최근 24시간 동안 피해 대상 5명/개의 객체에 접근해 위반 5건을 냄 (기준 5)
```

**중복 방지:**
- 같은 사용자·같은 창에서는 창 길이만큼 다시 경보하지 않습니다.
- 짧은 창(급속)에서 경보가 나면 긴 창(저속)도 함께 대기합니다. 같은 사건이 두 번 보고되지 않게 하기 위해서입니다.

**Wazuh 빈도 룰과 다른 점:** Wazuh는 "요청이 몇 번"인지는 세지만 **"피해자가 몇 명"인지는 모릅니다.** 주인 정보는 R1~R3·R5가 만들어 주기 때문에 Python에서만 가능한 판정입니다.

---

### BOLA-R5: 경로 주인 불일치

| 항목 | 내용 |
|---|---|
| 조건 | 응답에 주인 정보가 없고, **경로의 사용자 번호**가 요청자와 다름 |
| 주인 정보 출처 | URL (`config.yaml`의 `path_owners`) |
| 대상 API | 경로 ID가 곧 사용자 번호인 API: `/members/{id}`, `/profiles/{id}` 와 그 하위 경로 |
| 심각도 | high |

```
요청자 1  GET /members/2/addresses → 200   응답 []  (주소 없는 회원 → resp_ids 없음)
  · R1 불가 (응답에 주인 없음)
  · 경로 /members/{id} 의 사용자 = 2  ≠ 요청자 1  →  BOLA-R5
```

- **순서:** R1(응답) → **R5(경로)** → R2(장부) → R3. 응답이 가장 확실하고, 경로는 장부보다 확실하기 때문입니다.
- **장점:** 장부가 비어 있어도 요청 한 건으로 판정됩니다. 본문이 없는 `HEAD` 요청도 잡습니다.
  본인 경로(`PATCH /members/1`을 1번이 요청)는 정상으로 처리되어 R3 오탐도 막습니다.
- **주의:** `path_owners`에는 경로 ID가 **사용자 번호인 API만** 넣어야 합니다. `/orders/{id}`처럼 객체 번호인 API를 넣으면 오탐이 납니다.

### BOLA-R6: 순차 ID 탐색

| 항목 | 내용 |
|---|---|
| 조건 | `window_sec`(60초) 안에 같은 객체 종류에서, **본인 것이 아닌** 객체 ID가 `min_run`(5)개 이상 연속 (간격 `max_gap`(1) 이하) |
| 대상 요청 | 로그인한 일반 사용자의 **2xx와 403·404** (`statuses`). Kong 차단·admin 제외 |
| 판정 단위 | 사용자 (같은 사용자·같은 객체 종류는 창 길이 동안 1번만 경보) |
| 성격 | ID를 하나씩 바꿔 넣는 **정찰 행위** 경보. 성공 여부와 무관 |
| 심각도 | medium |

```
요청자 1  10초 동안  GET /orders/180 (404), 181 (403), 182 (200), 183 (404), 184 (200)
  → /orders/{id} 의 ID 180~184 5개 연속  →  BOLA-R6
```

- **본인 객체는 세지 않습니다.** 응답·경로·장부로 본인 것이 확인된 객체, 이전에 정상적으로 다룬 객체는 제외합니다.
  그래서 자기 주문 여러 개를 연달아 보는 정상 사용자는 걸리지 않습니다.
- `/members/1/addresses/5`처럼 상위 ID가 있으면 같은 상위 ID(`1`) 안에서만 연속을 봅니다.
- **Wazuh 룰과 다른 점:** Wazuh는 403/404가 "몇 번" 났는지 셉니다. R6는 그 ID들이 **연속인지**, 그리고 **본인 것이 아닌지**를 봅니다.
  성공(200)과 실패가 섞인 탐색도 하나로 묶습니다.
- **한계:** ID를 무작위로 고르거나, 창보다 느리게 훑으면 잡지 못합니다. 느린 공격은 R4(저속 창)가 보완합니다.

---

## 5. 판정하지 않는 것

| 경우 | 이유 |
|---|---|
| 403/404로 막힌 시도 | R1~R5에서는 판정하지 않음 (횟수 기반 탐지는 Wazuh 룰 담당). 단, 연속 ID 탐색은 R6가 봄 |
| 관리자(`role: admin`) 요청 | 남의 데이터를 보는 것이 정상 업무 (`exclude_roles`) |
| 로그인하지 않은 요청, Kong에서 차단된 요청(`blocked`) | 판정 대상이 아님 |
| 장부에 없는 객체의 **조회** | 정상 사용에서도 흔함. `unknown_owner`로 개수만 셈 |

## 6. 위반 로그 형식

`output/*.jsonl`에 한 줄에 하나씩 기록됩니다.

```json
{
  "event_time": "2026-10-29T00:11:35+09:00",
  "detected_at": "2026-10-29T00:11:40+09:00",
  "message": "이 로그는 BOLA-R2(장부 주인 불일치) 룰을 위반했습니다.",
  "rule": {"id": "BOLA-R2", "name": "장부 주인 불일치", "severity": "high", "description": "..."},
  "reason": "요청자 58이(가) 장부상 주인 36의 객체(POST /orders/91/cancel)에 접근해 200 응답을 받음 (장부 근거: confirmed)",
  "evidence": {"api": "POST /orders/{id}/cancel", "resource": "/orders/{id}", "object_id": "91",
               "requester": "58", "owners": ["36"], "owner_source": "ledger:confirmed"},
  "original": {"request_id": "...", "time": "...", "user_id": "58", "method": "POST",
               "uri": "/orders/91/cancel", "status": 200, "resp_ids": {"id": ["91"]}},
  "source": {}
}
```

| 필드 | 의미 |
|---|---|
| `message` | "이 로그는 OO 룰을 위반했습니다." |
| `reason` | 사람이 읽을 수 있는 판정 이유 |
| `evidence.owners` | 판정에 쓴 주인. R4에서는 피해 대상 목록 |
| `evidence.owner_source` | 주인을 알아낸 방법: `response:<필드>`(R1), `ledger:confirmed`/`ledger:inferred`(R2), `unknown`(R3), `aggregate`(R4), `path:<경로>`(R5), `sequence`(R6) |
| `original` | 원본 Kong 로그 요약 |
| `source` | Indexer 문서 정보 (실시간 모드일 때) |

R4는 여기에 `window`, `violation_count`, `rules`, `request_ids`, `first_time`, `last_time`이 추가됩니다.
R6는 `ids`(연속 ID), `statuses`(상태 코드별 건수), `window_sec`, `request_ids`, `first_time`, `last_time`이 추가됩니다.
